The Inventory service correctly applies the structural shell of Hexagonal Architecture — use-case ports, adapter annotations, and repository interfaces live in the right layers. The Inventory aggregate root carries meaningful business behavior and domain exceptions are well-named. However, two critical defects undermine correctness: the Outbox pattern is absent despite being a stated design goal, and ConfirmStockReservationService never updates inventory quantities after confirming a reservation, leaving the aggregate in a permanently inconsistent state.

Critical Issues

2
Critical Outbox pattern is entirely absent — domain events are never published ▼
Location
db/migration/V1__init_inventory_tables.sql domain/event/ (no publisher)
Impact

The design claims to implement the Outbox pattern, but there is no outbox_events table in the schema and no event publisher class anywhere in the codebase. State changes (StockReserved, ReservationExpired, StockAdjusted) are committed to the database but never propagated to downstream contexts (Order, Notification, Analytics). This means the Order BC cannot learn that stock has been reserved — the saga cannot progress. Without Outbox, stock mutations and event publication are not atomic, violating the core guarantee the pattern was chosen to provide.

Recommendation

Add an outbox_events table. After each aggregate mutation, write a serialized domain event to that table in the same transaction. A separate relay process (or Debezium CDC) reads committed rows and publishes to Kafka, then marks them processed.

Critical ConfirmStockReservationService never calls inventory.confirmReservation() — stock quantities never reflect fulfilled orders ▼
Location
application/service/ConfirmStockReservationService.java:25–42
Impact

When an order is paid, ConfirmStockReservationService.confirm() marks StockReservation records as CONFIRMED but never loads Inventory and never calls inventory.confirmReservation(quantity). The domain method that decrements both reservedQuantity and quantity is never invoked. The result: Inventory.reservedQuantity stays permanently elevated after each confirmed order. Over time, availableQuantity() returns values that are less than the actual available stock, which will erroneously block future reservations.

Recommendation

After updating reservations, load each related Inventory, call inventory.confirmReservation(reservation.getQuantity()), and persist the inventory. Group by inventoryId to batch the calls efficiently.

High Issues

3
High Native SQL UPDATE in SpringDataInventoryRepository bypasses the Inventory aggregate entirely ▼
Location
infrastructure/persistence/jpa/SpringDataInventoryRepository.java:20–29 application/repository/InventoryRepository.java:31
Impact

SpringDataInventoryRepository.reserve() executes a raw UPDATE inventories SET reserved_quantity = reserved_quantity + :quantity WHERE ... directly in the database. No Inventory object is loaded; Inventory.reserve() is never called; the availableQuantity() guard is never checked; and the domain exception InsufficientStockException is never thrown. This path exposes the service to silent over-reservation. This raw method is also exposed as a port method in InventoryRepository, leaking SQL semantics into the application boundary.

Recommendation

Remove InventoryRepository.reserve(). ReserveStockService already correctly loads the aggregate and calls inventory.reserve() — the native query path appears to be dead code or a remnant of an earlier approach. Verify no caller depends on it and delete both the interface method and the native query.

High AdjustStockService directly depends on DynamoDbTenantInfoRepository — infrastructure leaks into the application layer ▼
Location
application/service/AdjustStockService.java:13 application/service/AdjustStockService.java:32–34
Impact

AdjustStockService imports and injects DynamoDbTenantInfoRepository — a concrete AWS infrastructure class. This breaks the Dependency Inversion Principle: the application layer now depends on a specific cloud technology. Unit testing the service requires mocking DynamoDB; replacing DynamoDB requires editing the application service.

Recommendation

Introduce a TenantRepository port interface in application/repository. Implement it in infrastructure with DynamoDbTenantInfoRepository as a delegate. The application service depends only on the interface.

High ProductCreatedEvent is placed in the domain layer — it is an external integration event, not a domain event ▼
Location
domain/event/ProductCreatedEvent.java
Impact

ProductCreatedEvent is a contract owned by the Product bounded context, not by the Inventory domain. Placing it in domain/event blurs the boundary between what this context owns and what it consumes. Domain events should represent things that happened within this bounded context. This class should live at the infrastructure boundary where it is consumed.

Recommendation

Move ProductCreatedEvent to infrastructure/message/dto (or a dedicated acl package). The ACL translation in ProductCreatedConsumer maps this external DTO to an internal CreateInventoryCmd — the DTO should live next to the consumer that uses it.

Medium Issues

3
Medium ReleaseStockReservationUseCase is an empty interface with no service — a business capability is unimplemented ▼
Location
application/usecase/reservation/ReleaseStockReservationUseCase.java
Impact

The StockReservation domain model has a release() method and Inventory has a release(quantity) method — both well-implemented. But the use case that orchestrates them (e.g., when an order is cancelled before payment) has never been written. Stock locked by a cancelled order can only be freed via the expiry timer, not on demand.

Recommendation

Implement ReleaseStockReservationService mirroring the pattern in ExpireByInventoryTransaction: load reservations by orderId, call stockReservation.release(), sum quantities, load Inventory, call inventory.release(totalQty), persist both.

Medium Aggregate boundary between Inventory and StockReservation is ambiguous — consistency is not guaranteed by the model ▼
Location
domain/model/StockReservation.java application/repository/StockReservationRepository.java
Impact

StockReservation has its own repository (implying a separate aggregate root) but it is not explicitly declared as one. The invariant that Inventory.reservedQuantity == SUM(active reservation quantities for that inventory) must always hold, but nothing in the domain model enforces it — it relies entirely on the application layer executing both mutations atomically. If any service calls only one side, the invariant silently breaks (as already demonstrated by ConfirmStockReservationService).

Recommendation

Make the design decision explicit. Option A: make StockReservation part of the Inventory aggregate (embed reservations as a collection on Inventory) — the aggregate root enforces the invariant directly. Option B: keep them as separate aggregates and document that the application layer must always update both, with a transaction-scoped consistency test.

Medium StockMovement.referenceId is never populated — the audit ledger loses traceability ▼
Location
domain/model/StockMovement.java:37–48 infrastructure/persistence/entity/StockMovementEntity.java:56–59
Impact

StockMovement.newInstance() accepts reason but never populates referenceType or referenceId. The schema has reference_type and reference_id columns with an index on both. Without these, it is impossible to answer "which order triggered this stock movement?" or "which adjustment request removed these 50 units?"

Recommendation

Add referenceType and referenceId parameters to StockMovement.newInstance(). In AdjustStockService, pass the adjustment command's ID or the SKU as the reference; in reservation-driven movements, pass the orderId.

Prioritized Recommendations

1
Fix ConfirmStockReservationService to call inventory.confirmReservation() P0 — Correctness
Load the Inventory aggregate for each confirmed reservation, call inventory.confirmReservation(qty), and persist it in the same transaction. Without this, Inventory.reservedQuantity grows without bound and future reservations will be incorrectly rejected.
2
Implement the Outbox pattern P0 — Architecture
Add an outbox_events table. In each use-case transaction, write a serialized domain event row alongside the aggregate mutation. Deploy a relay (polling or CDC via Debezium) that publishes committed events to Kafka. This is the core guarantee the pattern was chosen to provide, and it is entirely missing.
3
Remove InventoryRepository.reserve() and the native SQL shortcut P1 — DDD Integrity
Delete the native UPDATE path that bypasses the aggregate. ReserveStockService already follows the correct flow. The raw SQL path is dead code that could be accidentally reactivated and will silently violate domain invariants.
4
Abstract DynamoDB behind a TenantRepository port interface P1 — Hexagonal Conformance
Introduce application/repository/TenantRepository. Move the DynamoDbTenantInfoRepository dependency to infrastructure. Application services should not know they are talking to DynamoDB.
5
Implement ReleaseStockReservationService and wire up OrderCreatedEventConsumer P1 — Feature Completeness
The domain model supports both operations fully. Only the application orchestration and the Kafka wiring are missing. Without order-cancellation release, stock is held until the 30-minute expiry regardless of what the customer does.
6
Move ProductCreatedEvent to infrastructure/message/dto and populate StockMovement.referenceId P2 — Cleanliness
Relocating the external event DTO clarifies aggregate ownership. Populating referenceType and referenceId on StockMovement makes the audit ledger queryable — the schema already has the column and index.
